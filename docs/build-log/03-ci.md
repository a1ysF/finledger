# Build 03: CI, tests run on every push

## Summary

Added continuous integration with GitHub Actions. Every push and pull request now runs the full `core` test suite, including the Testcontainers tests against a real PostgreSQL 16, on a fresh Ubuntu machine. A status badge in the README shows the result on `main`. The pipeline was shown to work in both directions: green on a clean commit, red on a deliberately broken assertion, green again after the revert.

## What was built

- `.github/workflows/ci.yml`: one job, `core (mvnw verify)`, on `ubuntu-latest`, triggered by `push` and `pull_request`:
  1. `actions/checkout@v7`
  2. `actions/setup-java@v6`: Temurin 21, Maven dependency cache keyed on `core/pom.xml`
  3. `./mvnw -B verify` in `core/`
- `core/mvnw` marked executable in Git (`100644` → `100755`).
- CI badge in `README.md`; CI row in the `CLAUDE.md` Commands table.
- No application code changed.

## Key decisions and trade-offs

- **Run the same command as a developer does.** CI runs `./mvnw verify` through the Maven wrapper, not a Maven installed on the runner. Laptop and CI therefore use the same Maven version (pinned in `.mvn/wrapper/maven-wrapper.properties`), and "passes locally" means the same as "passes in CI". Trade-off: the wrapper downloads Maven (about 10 MB) on each run, because only `~/.m2/repository` is cached.
- **No database secrets in CI.** Tests get their database from Testcontainers, and `@ServiceConnection` supplies its URL and credentials in place of the `${DB_...}` placeholders. The throwaway database holds no real data, so CI needs no secrets, and `infra/.env` stays local and git-ignored.
- **Linux runner.** GitHub's Ubuntu runners have Docker preinstalled, which Testcontainers needs. It also runs the code on the same OS family it will be deployed to (EC2, Build 21).
- **Least privilege.** The workflow token is `contents: read`, so the job can read the code but can't push or change the repository.
- **Fixed a Windows-to-Linux difference up front.** The repo was created on Windows, so Git recorded `mvnw` without the executable bit, and `./mvnw` would have failed on Linux with `Permission denied`. `git update-index --chmod=+x` sets the bit in Git without changing the file.
- **Kept small on purpose.** Required status checks (branch protection), uploading test reports on failure, and cancelling superseded runs were left out. Each is a small later addition.

## Concepts demonstrated

| Concept | Where it lives |
| --- | --- |
| Continuous integration, triggers, runners, jobs, steps | `.github/workflows/ci.yml` |
| Exit codes decide pass/fail | the `./mvnw -B verify` step |
| Dependency caching keyed on a file hash | `setup-java` `cache: maven`, `cache-dependency-path` |
| Least-privilege workflow token | `permissions: contents: read` |
| Containerised integration tests on CI | Testcontainers + `@ServiceConnection` in `TestcontainersConfiguration.java` |
| Executable bit tracked by Git | `core/mvnw` mode `100755` |
| Automated regression testing | every push reruns all 11 tests |

## How it's tested

The pipeline was tested by its own behaviour on real commits on branch `build-03`:

1. Workflow added → **green**: `Tests run: 11, Failures: 0`, Postgres started by Testcontainers on the runner.
2. `AccountApiTest` line 46 changed to expect `"1.00"` for a new account's balance → **red**: `Failures: 1`, `BUILD FAILURE`.
3. Assertion restored → **green**.

Locally, `cd core && ./mvnw -B verify` gives the same result: 11 tests, 0 failures.
